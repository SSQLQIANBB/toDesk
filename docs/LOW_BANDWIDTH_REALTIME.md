# 小带宽服务器的实时通信方案

## 当前数据路径

- 私信、群消息、在线状态和通话邀请走同一条 Socket.IO 连接；浏览器优先建立 WebSocket，失败时回退到 HTTP 长轮询。
- 新连接认证后收到一次在线用户快照。后续上线、下线、状态变化只广播该用户的增量。断线重连会重新认证并获取快照，不依赖可能丢失的历史状态事件。
- 私信先写入 MySQL，再推送到收件人的在线连接。客户端重新认证后查询未读私信，按消息 ID 去重，补上断线期间的私信。
- 群消息写入 MySQL，打开群聊时查询最近记录；已经加入群组的客户端实时收到推送。群组房间在重新认证后重新加入。
- 静态资源已有 gzip/Brotli 预压缩和带哈希文件名的长期缓存；Nginx 对 `/meeting` 已配置 WebSocket Upgrade 和长连接超时。

## 此次优化的效果与边界

过去每次在线状态变化，后端向每个客户端发送完整在线名单。若有 N 个在线用户，一次变化的名单传输量随 N² 增长。改成增量后，状态变化只向每个客户端发送一个用户的信息，约随 N 增长；全量名单仅在认证和重连时发送。状态不变时不广播。

WebSocket 优先可省去通常先建立 HTTP 长轮询再升级的请求；WebSocket 不可用时仍可回退。状态和普通消息共享连接，避免为联系人列表另开轮询。这个改动减少协议开销，但不能保证网络中断时事件必达。

Socket.IO 默认保证已送达事件的顺序，但并不保证断线时消息一定送达。当前私信依靠数据库和未读接口补偿；**群消息在用户离开页面或断线期间不会产生全局未读补偿**，只是打开群聊后能看到数据库中的最近记录。发送方目前采用乐观展示，服务端写入失败时也没有确认回执。这两项是后续要解决的可靠性缺口，不能把“页面上显示已发送”视为服务器已保存。

## 建议的下一步，按优先级实施

1. **消息确认与幂等**：每条私信、群消息附客户端生成的唯一 ID；服务端用唯一约束去重，写库成功后返回确认；客户端超时后安全重试，待确认/失败状态明确显示。只有确认写库才显示“已发送”。
2. **群消息断线补偿**：保存各群已处理的消息游标。重连时只拉取游标之后的群消息和未读数，而不是轮询所有群的 50 条历史；按消息 ID 去重。接口要校验群成员权限并设置每页上限。
3. **推送范围**：若联系人关系已固定，在线状态只推给该用户的联系人，避免向全站用户广播；用户多时这比继续压缩字段更有效。当前系统的“联系人”包含在线用户和私信历史联系人，后端尚无完整的好友关系模型，因此不能直接缩小广播范围，否则可能丢失联系人状态。
4. **媒体流限速**：视频和屏幕共享的码率通常远高于文字、状态事件。先测服务器实际出站带宽、WebRTC 是否走 TURN 中继，再设定分辨率、帧率和发送码率上限；网络变差时优先降低视频质量，保留音频和信令。多人 P2P/TURN 场景需要按参与人数估算总上行，单靠消息层优化无法抵消媒体流。
5. **资源与监控**：用浏览器 Network 看 `/meeting` 是否使用 WebSocket、断线重连次数和消息到达延迟；在服务器监控 95 分位出站带宽、连接数、数据库写入延迟及消息确认耗时。按实际瓶颈调整，避免盲目缩短心跳或增加轮询。

部署时保持 `/meeting` 的 WebSocket Upgrade；不要在反向代理中缓存消息或状态接口。若以后部署多个后端实例，需要共享 Socket.IO 事件与房间状态，并考虑长轮询的粘性会话；当前单实例部署没有这个要求。
