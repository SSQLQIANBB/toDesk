# 小带宽服务器的实时通信方案

## 当前数据路径

- 私信、群消息、在线状态和通话邀请走同一条 Socket.IO 连接；浏览器优先建立 WebSocket，失败时回退到 HTTP 长轮询。
- 新连接认证后收到一次在线用户快照。后续上线、下线、状态变化只广播该用户的增量。断线重连会重新认证并获取快照，不依赖可能丢失的历史状态事件。
- 私信先写入 MySQL，再推送到收件人的在线连接；发送方收到写库 ACK。客户端重新认证后查询未读私信，按消息 ID 去重，补上断线期间的私信。
- 群消息写入 MySQL，发送方收到写库 ACK；打开群聊时查询最近记录。客户端保存各群消息游标，重新认证后按游标补齐断线期间消息；群组房间在重新认证后重新加入。
- 静态资源已有 gzip/Brotli 预压缩和带哈希文件名的长期缓存；Nginx 对 `/meeting` 已配置 WebSocket Upgrade 和长连接超时。

## 此次优化的效果与边界

过去每次在线状态变化，后端向每个客户端发送完整在线名单。若有 N 个在线用户，一次变化的名单传输量随 N² 增长。改成增量后，状态变化只向每个客户端发送一个用户的信息，约随 N 增长；全量名单仅在认证和重连时发送。状态不变时不广播。

WebSocket 优先可省去通常先建立 HTTP 长轮询再升级的请求；WebSocket 不可用时仍可回退。状态和普通消息共享连接，避免为联系人列表另开轮询。这个改动减少协议开销，但不能保证网络中断时事件必达。

Socket.IO 默认保证已送达事件的顺序，但并不保证断线时消息一定送达。私信依靠数据库和未读接口补偿；群消息依靠按群保存的 ID 游标补偿。发送方只有拿到服务器写库 ACK 才显示已发送，超时用相同客户端消息 ID 重试。首次安装此版本前没有历史游标，因此首次订阅从当时最新群消息开始；过去的群消息仍可在群聊历史中查看。

## 建议的下一步，按优先级实施

以下清单已按当前项目结构落地。推送范围一项受现有联系人模型限制，保留全站状态增量，避免漏报：

- 私信和群聊发送带 `clientMessageId`，服务器用 `message_receipts` 的唯一键在事务中去重，写库后 ACK 消息 ID。客户端在超时后以相同 ID 重试，页面显示发送中/失败。旧客户端不带 ID 的发送仍可使用，但没有重试幂等保障。
- 群消息接口增加 `afterId` 游标、成员权限校验及每页最多 100 条。浏览器按账号保存各群游标，重新认证后拉取增量并按 ID 去重；首次订阅从当时最新 ID 开始，历史仍由打开群聊时加载。
- 联系人仍包括可能与当前用户没有固定好友关系的在线用户和私信历史联系人。缩小状态广播范围会使部分联系人丢失在线变化，因此此项需等好友/联系人关系模型明确后再启用。
- 摄像头默认采集降到约 960×540、24fps，发送端视频上限约 900kbps；屏幕共享发送端上限约 1.8Mbps。个人共享请求的帧率为 15fps；群共享首次在点击入口时用浏览器默认约束取流，只有重新取流时才按页面质量档位请求分辨率和帧率。浏览器不支持 `setParameters` 时继续使用原有媒体流，音频不受限速影响。实际 TURN 流量仍需按下方方法测量。
- 服务器每分钟输出一次 `realtime_metrics`：连接数、WebSocket/轮询数、消息写入数、写入耗时 p95 和失败数。结合主机网卡 95 分位出站流量与 TURN 服务器流量判断瓶颈。日志不含消息正文或用户标识。

验证时先用浏览器开发者工具确认 `/meeting` 的连接类型和断网重连次数，再在服务器查 `realtime_metrics` 日志。网卡出站流量可用已有主机监控采样；若 WebRTC 连接经 TURN 中继，需同时监控 TURN 服务器出站流量。部署前后比较相同人数和相同媒体场景下的 p95 出站流量与消息确认耗时，不能仅看单次峰值。

1. **消息确认与幂等**：每条私信、群消息附客户端生成的唯一 ID；服务端用唯一约束去重，写库成功后返回确认；客户端超时后安全重试，待确认/失败状态明确显示。只有确认写库才显示“已发送”。
2. **群消息断线补偿**：保存各群已处理的消息游标。重连时只拉取游标之后的群消息和未读数，而不是轮询所有群的 50 条历史；按消息 ID 去重。接口要校验群成员权限并设置每页上限。
3. **推送范围**：若联系人关系已固定，在线状态只推给该用户的联系人，避免向全站用户广播；用户多时这比继续压缩字段更有效。当前系统的“联系人”包含在线用户和私信历史联系人，后端尚无完整的好友关系模型，因此不能直接缩小广播范围，否则可能丢失联系人状态。
4. **媒体流限速**：视频和屏幕共享的码率通常远高于文字、状态事件。先测服务器实际出站带宽、WebRTC 是否走 TURN 中继，再设定分辨率、帧率和发送码率上限；网络变差时优先降低视频质量，保留音频和信令。多人 P2P/TURN 场景需要按参与人数估算总上行，单靠消息层优化无法抵消媒体流。
5. **资源与监控**：用浏览器 Network 看 `/meeting` 是否使用 WebSocket、断线重连次数和消息到达延迟；在服务器监控 95 分位出站带宽、连接数、数据库写入延迟及消息确认耗时。按实际瓶颈调整，避免盲目缩短心跳或增加轮询。

部署时保持 `/meeting` 的 WebSocket Upgrade；不要在反向代理中缓存消息或状态接口。若以后部署多个后端实例，需要共享 Socket.IO 事件与房间状态，并考虑长轮询的粘性会话；当前单实例部署没有这个要求。
